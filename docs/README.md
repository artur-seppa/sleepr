# Notas de estudo — NestJS & Microserviços (projeto `reservations`)

Notas acumuladas enquanto estudo a arquitetura deste projeto. Divididas por tema para facilitar a consulta e a revisão.

## Índice

1. [Módulos e Injeção de Dependência](./01-modules-e-di.md) — `@Module()`, `providers`/`exports`, config direto em cada app (`ConfigModule.forRoot({ isGlobal: true })` + `.env` próprio + `ConfigService` na porta), por que cada módulo do `libs/common` aloca o que aloca, e os dois sentidos de "global".
2. [Mongoose — `forRoot` vs `forFeature`](./02-mongoose-forroot-vs-forfeature.md) — conexão global (uma vez, no root) vs. schemas registrados por módulo.
3. [Validação — `ValidationPipe` + DTOs](./03-validation-pipe-e-dtos.md) — como o payload é transformado e validado **antes** de chegar no controller (`whitelist`, `transform`, `@Type(() => Date)`).
4. [tsconfig no monorepo — erro `TS6059` / `rootDir`](./04-tsconfig-monorepo-e-rootdir.md) — por que acontecia ao importar `@app/common` e a correção aplicada.
6. [Logger — Pino via `nestjs-pino`](./06-logger-pino.md) — `LoggerModule` no `common` + `app.useLogger` no `main.ts`, configurado uma vez e reusado por todo microserviço.
7. [Autenticação — Passport, Guards, Strategies e `@CurrentUser`](./07-passport-guards-strategies-e-decorators.md) — como o `POST /auth/login` valida email/senha: `LocalStrategy` (regra) + `LocalAuthGuard` (gatilho) + `@CurrentUser()` (lê `request.user`) + `@Res({ passthrough: true })` (cookie), e o porquê do `import type { Response }`.
8. [Comunicação `auth` ↔ `reservations` via TCP](./08-comunicacao-auth-reservations-tcp.md) — como `reservations` autentica rotas sem ter `JWT_SECRET`: `ClientsModule` (cliente TCP) + `JWTAuthGuard` (common) chamando `@MessagePattern('authenticate')` no `auth`, que verifica o token (`AuthService.verifyToken`) e devolve o usuário.
9. [Por que microserviços (e por que TCP, não HTTP ou Kafka)](./09-por-que-microservicos.md) — trade-offs de TCP vs HTTP vs Kafka para comunicação interna, e o motivo (didático, não de escala) de separar `auth`/`reservations` neste projeto.
11. [Pagamentos — `payments` + Stripe](./11-payments-stripe.md) — o terceiro microserviço (só TCP, sem HTTP): `reservations` manda `create_charge` via `PAYMENTS_SERVICE`, `payments` tokeniza o cartão (`paymentMethods.create`) e cobra (`paymentIntents.create`) no Stripe; por que `CardDto` (e não o tipo do SDK), a validação do payload TCP por handler (`@UsePipes`) e o estado atual do passo de tokenização (`pm_card_visa` fixo).
12. [Notificações — `notifications` e eventos TCP](./12-notifications-eventos-tcp.md) — o quarto microserviço e a cadeia `reservations` → `payments` → `notifications`: `payments` é servidor de um e cliente do outro; `emit` + `@EventPattern` (fire-and-forget, sem resposta, sem garantia de entrega) vs `send` + `@MessagePattern`, Observable *hot* vs *cold*, por que o `email` é injetado por `reservations` a partir do usuário logado, e o envio real com nodemailer + Gmail OAuth2 (incluindo o `TS2729` de montar o `transporter` fora do construtor e o `await` no controller para a falha do envio não derrubar o processo).
13. [Deploy — Artifact Registry (Google Cloud)](./google%20cloud/container.md) — publicando a imagem do `reservations` na nuvem: criar um repositório Docker por microserviço, `gcloud auth configure-docker` como *credential helper* (por que não é um login), a anatomia do caminho `host/projeto/repo/imagem:tag`, por que o contexto do `docker build` tem que ser a raiz do monorepo, o erro `. is not a regular file` de trocar `-f <dockerfile> <contexto>` de lugar, e o polimento do Dockerfile para copiar só `apps/reservations` + `libs` — que revelou a dependência invertida `libs/common` → `apps/auth` no `@CurrentUser()` (resolvida com o `UserDto`, sem mover o schema para o common).
